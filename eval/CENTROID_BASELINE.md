# Centroid categorizer baseline (issue #92, Slice 4b)

First measured comparison of the prototype/centroid semantic categorizer
against the deterministic `builtin` keyword pass, using the #88 harness.

Reproduce with:

```bash
cargo run -p finsight-eval --bin centroid_eval
```

## Result

Corpus: `eval/categorization_corpus.synthetic_multi_archetype.jsonl`
(2,751 examples · 330 unique merchants · 10 categories, **provenance: synthetic**)
Split: merchant-disjoint, 1,988 reference / 763 holdout, seed 42
Encoder: `sentence-transformers/all-MiniLM-L6-v2` (384 dims)
Abstain floor: cosine ≥ 0.35 (`MIN_PROPOSAL_SCORE`, same constant the shipped pass uses)

Scored on the **merchant-disjoint holdout only** — 763 rows whose merchants
appear nowhere in the reference half the prototypes were built from.

| source     | coverage | precision | correct |
|------------|---------:|----------:|--------:|
| `builtin`  |   16.6%  |   100.0%  | 127/127 |
| `centroid` |   98.0%  |    97.7%  | 731/748 |

## Reading this honestly

**The headline is coverage, not precision.** The deterministic pass is right
whenever it fires, but it only fires on 1 transaction in 6 — by construction,
since it predicts only when a keyword table matches. Its 100% is a statement
about a narrow, easy slice, not about the ledger. The centroid pass answers
**six times as many** transactions and is wrong about 2 in 100 of them.
That is the tradeoff Slice 4b exists to expose, and it is why semantic matches
route to review instead of being applied.

**This does NOT discharge epic #74's ≥98% merchant-disjoint gate**, for three
independent reasons, any one of which is sufficient:

1. **The corpus is synthetic.** It is invented data whose whole purpose is to
   exercise the harness. The loader carries `provenance: synthetic` into every
   report specifically so this number cannot be restated as a real-world
   precision claim. 97.7% here is not evidence of 97.7% on a real ledger.
2. **Synthetic descriptors are almost certainly easier than real ones.** The
   corpus is generated by `eval/generate_synthetic_corpus.py`, so its merchant
   strings carry whatever regularities that generator has. Real bank
   descriptors are noisier — truncations, store numbers, processor prefixes
   (`SQ *`, `TST*`), inconsistent casing, and the same merchant formatted
   differently by different banks. An embedding model plausibly exploits
   generator regularities that will not exist in production. Expect the real
   number to be **lower**, not equal.
3. **The gate is about auto-apply, and nothing here auto-applies.** Even at
   99%, the centroid pass would still write proposals only. Flipping any
   confidence band to auto-apply is issue #93's decision, and #93 requires
   issue #89's *real* corpus — currently blocked on a real-label source
   (#94's review surface, unshipped).

**What it does establish.** The plumbing is real and measurable: prototypes
built from one set of merchants generalize to a disjoint set well enough to be
worth reviewing, the abstain floor behaves (2% of holdout rows draw no
prediction rather than a guess), and the harness can now compare a semantic
source against the deterministic baseline on identical rows. That is what
Slice 4b was scoped to deliver.

## Error analysis — where the 2% actually goes

`centroid_eval` prints this; it is the evidence for choosing among Slice 7's
(#95) experiments rather than picking one by taste.

**Every one of the 17 misclassifications comes from three merchant families,
and 16 from two:**

| actual → predicted | n | example |
|---|--:|---|
| `utilities` → `groceries` | 11 | `BLUESAIL HYDRO PAYMENT #3561` |
| `subscriptions` → `housing` | 5 | `Norwood Membership Fee #1977` |
| `transport` → `groceries` | 1 | `YONDERHILL TRANSIT AUTHORITY` |

**All 15 abstains are the same two families**, scoring 0.29–0.34 — just under
the 0.35 floor (`POS PURCHASE BLUESAIL HYDRO PAYMENT` at 0.332,
`QUILLMARK MEMBERSHIP FEE` at 0.305).

So the failures are **not** diffuse noise at the decision boundary. They are a
small number of *systematic lexical traps*, each hitting every transaction of
an affected merchant.

### The "hydro" trap is real, not a synthetic artifact

`BLUESAIL HYDRO` is invented, but the confusion it triggers is not: **BC Hydro,
Hydro One and Hydro-Québec are real electricity utilities**, and a
general-English sentence encoder reasonably places "hydro" near water and
produce rather than near power bills. Any Canadian user's real ledger would hit
exactly this. The same shape applies to other regionalisms a general encoder
has no reason to know (`Eskom`, `Hydro Ottawa`, `SaskPower`).

### What this implies for #95's menu

- **A reranker is the wrong tool here.** Reranking reorders candidates within
  the same embedding space; it does not fix a prototype that genuinely sits
  closer to the wrong category. These errors are not near-ties being ordered
  badly — `utilities` is losing to `groceries` outright, 11 times.
- **Per-category examples are the cheap, already-built lever.** One `BC HYDRO`
  example on `utilities` moves that centroid directly, and #91 already ships
  the mechanism plus a UI path to add one. This is not an #95 experiment at
  all — it is the existing feature doing its job, and it is worth measuring
  before anything heavier is considered.
- **A constrained LLM fallback targets the abstains specifically.** All 15 sit
  in a narrow band below the floor on two merchant families; an LLM knows what
  "BC Hydro" is. That is a well-shaped, bounded fallback (2% of rows), not a
  general second pass.
- **Multilingual is not implicated** by this corpus — every row is English. It
  needs its own corpus before it can be evaluated at all.

The honest ordering, then, is: measure the examples lever first (free, shipped),
then scope the LLM fallback against the abstain band, and treat reranker and
SetFit as unmotivated by the current evidence.

## Method notes

- Prototypes are built from the **reference half only**. Building them from the
  full corpus and then scoring the holdout would leak merchant identity across
  the split; the number would rise and mean nothing. The binary re-asserts
  `merchant_sets_disjoint` at runtime rather than trusting the split.
- Both sources are scored over the **same holdout rows**. Comparing precision
  across different populations would make the two lines incomparable.
- An abstain counts against **coverage**, never precision — matching the
  production pass, which declines to propose rather than filling the review
  queue with noise.
- The centroid math is `finsight_agent::embedding::centroid`, the same code the
  shipped pass runs. The harness deliberately does not carry its own copy: a
  benchmark measuring a private reimplementation would be measuring something
  the app does not execute.

## When to re-run

Re-run and update this file when the encoder changes (`model_id`), when the
abstain floor moves, or when the corpus grows. If a **real** corpus ever lands
(issue #89), run it against that instead and record both — the synthetic figure
stays useful as a harness regression check, but only the real one speaks to the
epic's gate.
